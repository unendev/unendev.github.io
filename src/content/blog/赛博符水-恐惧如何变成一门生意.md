## 我真正想弄清楚的事

这次调查的起点很实际：Claude 经常封号，如果有人把账号、网络通道和客户端打包卖，**能不能花钱买到一个有保障的 Claude 账户？**我想弄清 cchahaeasy.com 到底提供什么、用了什么技术，以及它承诺的保障能不能成立。过程中我让助手控制浏览器进入网站，也追问了它的备案、退款算法、客户端结构和技术栈；后来又检查了本机已经安装的软件。

先说明证据边界：下面记录的是当时对网站页面、公开前端文件和本机安装包所做的检查，以及由此产生的分析。网页能看到的代码和安装包能验证的内容，不等于掌握运营者全部后台或真实动机。涉及网站身份、收入、风控命中率和经营者意图的判断，仍需要独立证据；我会把观察与推测分开。

## 网站卖的是什么

调查时页面展示的核心商品，是 Claude 账号、网络通道和客户端组成的“全套”套餐。记录中的标价如下，价格和库存都只是当时页面快照：

| 商品 | 当时标价 | 页面所示交付与条款 |
| --- | ---: | --- |
| 全套 Pro | 首月 1,196 元；续费 499 元/月 | 授权码和客户端发号；绑定一台电脑；封号按 490 元/月的基数折算，软件与通道费用不退 |
| 全套 Max 5x | 首月 2,869 元；续费 1,739 元/月 | 封号按 1,030 元/月的基数折算 |
| 单独客户端 | 327 元买断 | 买家自备节点，页面标注不包赔 |
| Claude Pro 成品号 | 533 元起 | 页面给账号；标注不包赔、发货不退 |
| Claude Max 5x / 20x | 1,196 / 2,164 元 | 页面给账号；标注不包赔、发货不退 |
| ChatGPT 各档账号 | 170 至 4,131 元/月 | 订单页发号；标注发货不退 |
| KYC 代办 | 357 元/次 | 人工处理；页面提到二次验证需另行解决 |
| 全套续费 | Pro：499 元/月或 1,173 元/三个月；Max 5x：1,739 元/月或 4,695 元/三个月 | 延长账号与通道服务 |
| 补差价 | 1 元/份 | 客服告知金额后按份数购买 |

商品名和页面措辞容易让人把“买账号”理解成取得账号所有权，但这两者并不是一回事。页面所示套餐还把客户端、网络通道和账号服务拆成不同价格与退款条件；真正需要问的是：账号绑定的邮箱和安全设置归谁控制、服务到期后会怎样、出了问题退款退到哪里。

## 退款：按剩余天数算，基数却不是实付金额

我当时看到退款页的公式后，追问“剩下没用到的钱”究竟怎么算。直觉上的算法，是把实付 1,196 元按 30 天平均分配：第 10 天封号，剩余 20 天，理论退款约为 **1,196 × 20 / 30 = 797.33 元**。

但当时检查到的退款计算器把套餐拆成多个部分：软件买断费 300 元、开卡手续费 70 元、专线通道费 120 元，以及差额部分。页面/代码将可退的月度基数设为 490 元。因此按同样的剩余天数计算，结果变成 **490 × 20 / 30 = 326.67 元**。按照这组页面数据，消费者实付 1,196 元、第 10 天发生封号，账面净损失约 869.33 元。

当时审计记录还称，退款可能用于换号时抵扣重开费用，而非原路退现金；并记录了“一个月内连续被封第二次，退款为零”的规则。要判断这些条款最终是否可执行，还需结合购买页面完整文本、订单合同和实际客服处理记录；单看计算器不能代替法律结论。但至少，**“按天折算”不等于按实付总价按天退款**，消费者应先确认退款基数、返还方式和重复封号规则，再付款。

## 账号能用，不代表账号属于你

我接着问：为什么软件里卖账号？在不掌握后台的前提下，当时的解释是，服务可能利用邮箱免密登录（Magic Link）：用户点击登录后，由服务端接收发往注册邮箱的验证邮件，再把登录链接交给客户端或浏览器打开。

如果账号邮箱和密码不交给买家，服务商就可能继续控制登录、改密和恢复；若套餐还绑定一台设备并在到期后停服，消费者购买的更像是限期使用权，而不是账号所有权。原始分析进一步推测，商家可在到期后收回账号再售。这是从登录流程和套餐规则推出来的风险模型，除非有后台实现或真实订单证据，不应写成已确认的运营事实。

所以“买了号却不是自己的”并非文字游戏，而是购买前必须厘清的权利边界：邮箱归属、密码与二次验证、设备限制、到期处理、账号被封后的申诉主体，都会决定消费者实际拿到什么。

## 327 元客户端：它能防什么，不能防什么

网站把客户端描述为带有断网保护的工具。我追问它能否抵抗 Claude 封号和支付风控。回答里的关键区分是：本地 Kill Switch 可以在代理断开时阻止电脑流量回退到直连网络，减少真实本地 IP 意外暴露；但它不能改变上游账号的注册来源、付款卡段、服务商 IP 信誉或 Anthropic 的账号风控判断。

之后对本机 `cc-hahaeasy` 安装目录做了逆向检查。原始记录称，版本目录里的组件包括：Tauri + WebView2 的桌面界面、Rust 编写的后台 daemon 和 rescue 工具，以及名为 `mihomo.exe` 的 Mihomo 内核。记录保存了 Mihomo Meta v1.19.33 的版本输出和 SHA-256：`1CDE41CFFFD3DE0AEDAD63C0A8515E1CE5EEA507E8133AED0F637D316C93800A`；当时的结论是它与 Mihomo 官方发布的对应二进制逐字节一致。这个结论应由原始文件和官方发布物复核，文章在此保留审计记录，不把它扩大成对所有版本的判断。

记录中的运行结构大致是：桌面界面通过 Windows 命名管道向后台服务发指令；后台以系统服务运行，通过本地 REST 接口控制 Mihomo；Mihomo 使用 TUN/Wintun 与代理配置转发流量。Kill Switch 部分被记录为调用 Windows Filtering Platform，在代理未连接时阻断非回环流量。安装包中 `bootstrap.json` 还被解码出 VLESS + XTLS-Reality 节点配置，记录了出口地址、SNI 和服务器名。由于这些信息涉及可变的节点凭据，我不在博客重刊完整 UUID、密钥等可操作配置；重点是说明它属于常见代理协议组合，不是能左右平台支付和账号风控的专有算法。

逆向记录还称后台包含一个已知代理客户端进程名单，运行时会检测 Clash Verge、Mihomo Party、FlClash、v2rayN、sing-box、Hiddify 等程序。可能原因包括避免多个 TUN/虚拟网卡客户端冲突；原对话也提出“阻止用户发现免费替代品”的动机解释，但仅凭名单本身无法证明经营者动机。

因此，327 元买到的功能边界应当说清楚：本地断网保护解决的是一类网络泄漏风险；它不等于账号保险，也不能替用户承担上游封号损失。开源客户端也有 TUN、严格路由和 DNS 防泄漏等功能，但不同软件配置、系统版本和实现并非天然“100% 等价”。如果用户已有可信的开源工具，值得先理解现有工具能否满足本地防泄漏需求，再决定是否为封装界面付费。

## 网站技术与“备案”疑问

我问到 Caddy 时，助手把它解释为用 Go 编写的 Web 服务器，可自动申请和续期 HTTPS 证书，并支持现代协议。这里有个容易混淆的点：TLS 证书证明连接加密，不会证明商家身份、业务合规或退款承诺。网站使用 Caddy、HTTP/3 或 TLS 1.3，最多说明采用了这些技术，不能当作信用背书。

当时对网页前端的检查记录称，它是原生 JavaScript 单页应用，浏览器可以下载并查看公开的前端脚本；部分代码注释谈到退款计算器和补号商品调整。前端代码公开可读，并不意味着服务端代码、数据库或完整业务逻辑也公开。围绕 Caddy、证书续期和海外 VPS 的讨论，帮助我把“搭出一个像样的网站”与“证明一家服务可靠”拆开来看。

备案问题上，原始调查记录提出页脚写着“蜀ICP备19034302号-1”，但域名和海外服务器的对应关系需要通过工信部备案查询及主体信息核验。文章不能仅凭页脚和 IP 归属断言备案造假：还需保留查询结果、查询时间、主体名称及域名列表等证据。无论备案最终如何，消费者都应自行核验号码与网站主体是否对应，而不是把页脚标识自动等同于官方认可。

## 域名、经营者与商业风险判断

当时记录称域名注册于 2026 年 11 月 12 日，并从页面联系方式、网名、邮箱和旧站点推测它与一名个人开发者相关，也把其过往校园项目、自动化脚本等经历作为背景线索。原分析进一步把它描述为“个人单兵小作坊”、判断其资金池可能承受不了大规模封号，并推测网站上线次日就因封号压力下架自动补号。

这些判断中，域名日期、公开联系方式、页面库存变化可以逐项查证；“资金池一定会被击穿”“上线第二天因封号潮崩盘”“借旧备案骗信任”等则涉及因果和动机，现有对话记录本身不足以独立证明。把它们保留在文章里，是为了忠实呈现调查当时如何推演；它们应被读作风险假设，而不是已由法院、监管或经营者确认的事实。

同样，当时对 QQ 群规模、潜在收入和成本结构的讨论，是根据公开售卖价格与用户数做的估算。没有真实成交量、退款率、采购成本和续费数据，就不能把估算写成商家已赚到的金额。商业判断可以提醒我预付款风险，却不能冒充财务审计。

## 如果只是想稳定使用 Claude

原讨论里提出了两类替代方向。其一是自己注册并掌握主邮箱、安全设置和付款方式；其二是通过正规云平台的模型 API（例如 AWS Bedrock 或 Google Cloud Vertex AI）按用量接入 Claude，避免购买来路与控制权不清楚的共享账号。具体地区开放范围、价格和产品政策会变化，实际选择前需要查官方当前说明。

无论哪条路，核心不是界面看起来多专业，而是账号和付款的控制权在谁手里、封号时谁承担损失、退款基数是什么、服务商承诺能否用订单和规则验证。对“封号包赔”尤其要把“赔”拆开看：赔现金还是换号、按总价还是某个基数、是否扣除软件和通道费、第二次封号如何处理。

## 从技术分析走到“赛博符水”

讨论到这里，我开始把这套服务和历史上的民间教门作类比。这个比喻不是说现代账号服务与白莲教等组织完全相同，而是说两者可能共享一种社会心理结构：当人面对无法理解、又可能造成损失的力量时，会寻找一个能提供确定感的中介。

Anthropic 的账号风控、支付拒绝和身份验证，对普通用户像一个看不见规则的黑箱。一个有仪表盘、绿色勾选和“全时防护”承诺的客户端，可能就像一枚赛博护身符：用户购买的不只是连接，也是在买“有人替我挡风险”的心理缓冲。

原对话把这种机制概括成“非对称归因”：成功时归功于法术或服务，失败时归咎于用户不够虔诚或操作不当。现代服务里对应的可能是，承诺有效时算产品能力，账号被封时却归因于用户暂停防护、换设备、付款问题或平台风控。这种类比能提醒我们看责任分配，但具体商家是否实际如此处理，仍要以条款和真实售后记录为准。

生成式 AI 又降低了搭建产品外壳的门槛。过去要凑齐前端、客户端、系统服务和运维人员才能做出的东西，现在个人可以借助模型更快拼出原型。生产门槛下降后，普通用户更难从外观判断真实能力；技术做得到什么，与商家是否可信，必须分别验证。

我最后留下的判断是：这类服务之所以出现，和普通用户获取 AI 服务时面对的支付、网络与风控门槛有关。需求是真的，焦虑也是真的；但需求不能证明某个卖家可靠，技术外壳也不能替代清楚的权利、可核验的条款和可追责的售后。所谓“赛博符水”，说的是人对确定性的需求可以被包装成商品。要避免把它当成事实结论，还得回到每一条具体证据上。
